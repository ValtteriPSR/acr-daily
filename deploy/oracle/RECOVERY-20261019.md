# Oracle recovery: 19 October 2026

Guest monitoring recorded a jump from about 32% to 96% memory use and a brief
100% CPU peak at 16:17–16:18 UTC. Guest metrics then stopped and public HTTPS
became unreachable. DNS still matched the running VM. Infrastructure health
metrics did not report a host fault. No matching previous-boot OOM entry was
found; the process responsible for the resource spike remains unconfirmed.

During recovery, memory pressure recurred after a backup trigger, initially
suggesting the backup was responsible. A later instrumented dump/upload/restore
completed successfully with a Python peak RSS of 57,644 KiB: 31 public tables
and four result rows were restored into a disposable database. Immediately
afterwards, a separate `dnf` process was measured at 1,217,748 KiB RSS, while
available host memory fell to 135 MiB. Guest memory then reached 94% and HTTPS
timed out. This identifies a large package-manager process during the recurrence;
it does not prove which process caused the original outage, whose logs are missing.
Persistent journal metadata assigned the DNF process to
`dnf-makecache.service`, which started at 19:12:37 UTC, immediately before the
measured spike. After the next reboot, stopping/disabling that timer and applying
its limit left no DNF process running and host RAM use returned to about 550 MiB.

## Package cache refresh and backup resource limits

Automatic package metadata cache refresh is unnecessary for serving the club.
On this small VM, `dnf-makecache.timer` is disabled. Package installation and
security-update services are separate and are not disabled by this change.
`dnf-makecache-memory.conf` is installed as
`/etc/systemd/system/dnf-makecache.service.d/90-memory-limit.conf` to bound a
future start of that unit to 384 MiB RAM and 64 MiB swap, with a 256 MiB soft
threshold. SELinux remains enforcing and audit logging remains enabled.

Applied on the host as root (configuration files are in this folder):

```sh
systemctl disable --now dnf-makecache.timer
systemctl stop dnf-makecache.service
install -D -m 644 dnf-makecache-memory.conf /etc/systemd/system/dnf-makecache.service.d/90-memory-limit.conf
systemctl daemon-reload
```

This affects automatic metadata prefetch only. Manual package management still
refreshes metadata when required and should be monitored on this small machine.

The scheduled backup template independently limits its worker and host
subprocesses to 512 MiB RAM and 128 MiB swap, with a 384 MiB soft threshold.
Processes started inside PostgreSQL's container use the container's cgroup.
Failed jobs retain the previously verified remote recovery copies. A CI test
touches an oversized allocation and requires a cgroup OOM kill; the disposable
probe omits soft throttling so it reaches the unchanged hard cap promptly.

The VM was restarted through OCI. After boot, PostgreSQL and the application
were active, while the Caddy gateway was inactive. Starting Caddy restored HTTPS.
The existing approximately 1.7 GiB swap file was retained unchanged.

## Gateway startup dependency

The Caddy Quadlet now uses `Wants=acr-app.service` with `After=acr-app.service`.
This starts the application alongside the gateway, while permitting the gateway
to start if the application's initial startup job fails and is retried. With
`Requires`, a failed initial backend job can leave the gateway inactive even
after the backend recovers. A backend crash should likewise not stop HTTPS.

The host unit was backed up before changing this dependency. The application,
database, network bindings and gateway authentication configuration are unchanged.

## Persistent, bounded diagnostics

The host now uses `journald-acr.conf` under
`/etc/systemd/journald.conf.d/90-acr-retention.conf`. Journals persist across
boots, with 64 MiB for persistent data, 32 MiB for runtime data, a 1 GiB
free-space reserve and seven-day retention. This preserves evidence for future
resource spikes while bounding disk use.

## Verification

`test_gateway_startup.py` reads the real gateway Unit dependencies and starts
disposable systemd probe units. The backend intentionally fails; the gateway
must still start. Probe services and files are removed afterwards. CI runs this
check on x86-64 and ARM64 Linux hosts:

```sh
sudo python3 deploy/oracle/test_gateway_startup.py
```
