# Oracle recovery: 19 October 2026

Guest monitoring recorded a jump from about 32% to 96% memory use and a brief
100% CPU peak at 16:17–16:18 UTC. Guest metrics then stopped and public HTTPS
became unreachable. DNS still matched the running VM. Infrastructure health
metrics did not report a host fault. No matching previous-boot OOM entry was
found; the process responsible for the resource spike remains unconfirmed.

The VM was restarted through OCI. After boot, PostgreSQL and the application
were active, while the Caddy gateway was inactive. Starting Caddy restored HTTPS.
The existing approximately 1.7 GiB swap file was retained unchanged.

## Gateway startup dependency

The Caddy Quadlet now uses `Wants=acr-app.service` with `After=acr-app.service`.
This starts the application alongside the gateway, while permitting the gateway
to start if the application's initial startup job fails and is retried. With
`Requires`, a failed initial backend job can leave the gateway inactive even
after the backend recovers. A backend crash should likewise not stop HTTPS.

The host unit was backed up before changing this dependency. The application,
database, network bindings and gateway authentication configuration are unchanged.

## Verification

`test_gateway_startup.py` reads the real gateway Unit dependencies and starts
disposable systemd probe units. The backend intentionally fails; the gateway
must still start. Probe services and files are removed afterwards. CI runs this
check on x86-64 and ARM64 Linux hosts:

```sh
sudo python3 deploy/oracle/test_gateway_startup.py
```
